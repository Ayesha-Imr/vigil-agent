vigil · how it works

An agent that keeps watch, and knows when to stay quiet.

vigil runs on a small server, all the time. You talk to it from the chat apps on your phone; it works in the background, and it interrupts you only when it is worth it. Every rule about when it may interrupt you is enforced by code and checked by a model checker, not left to a prompt.

built on pi ChatGPT (Codex) + OpenCode Go TypeScript · Node 22 · SQLite 5 TLA+ models ≈590 tests

02 · the attention governor

Seven rules decide whether your phone buzzes

Anything vigil says without being asked goes through offer(). Replies to your own messages skip it, since you asked. The rules run top to bottom and the first one that applies wins. Try it; the defaults are the shipped ones (3 interrupts a day, an hour apart, quiet 22:30–08:00).

    03 · an example day

    What that looks like over 24 hours

    An illustrative day under the default policy, in the spirit of vigil demo. Four things buzzed: one critical alert at night and three interrupts. Everything else waited for quiet hours to end, or was batched into a digest.

    critical: sent, even at night (max 3 a day) interrupt (max 3 a day, an hour apart) held or batched digest: one silent message quiet hours
    04 · acting on your behalf

    Risky actions wait for your thumb, and the shell is boxed in

    The life of an approval

    A press over the HTTP API is refused by default: any process that finds the token, the agent's own tools included, could otherwise approve its own call. Typed /approve, /mode and /login follow the same rule.

    Layers around your machine

    A watched page is judged by a model with no tools, so an injected instruction has nothing to call. Work that a page inspires gets read-only tools and no memory.

    05 · how we know it holds

    Four checks between a bug and your phone

    For the governor, a defect has to get past all four. The other risky parts (approvals, outbox, scheduler, workers) get the model check, and the outbox also gets trace validation.

    1 · model check

    TLA+ and TLC

    Every order of offers, ticks, replies, mutes and crashes, within small bounds.

    2 · property tests

    fast-check

    Random sequences against the real TypeScript, in four time zones.

    3 · trace validation

    Code refines model

    Recorded runs of the real code must be valid runs of the model, step by step.

    4 · runtime guard

    Before every send

    The rules are re-checked against the delivery history in the database.

    ModelWhat it promisesStates exploredMutants caught
    GovernorBudget, gap, critical cap, quiet hours, mutes, no duplicates, nothing lost or told twice405,96319 / 19
    ApprovalsOnly an approved, exact, unexpired call runs, once; only you can approve325,26310 / 10

    SchedulerOne run per slot, no overlap, nothing lost across a crash250,7379 / 9
    WorkersNo ticket runs twice; your message is never starved or silently lost432,44312 / 12

    A mutant is a deliberately broken copy, for example "skip the gap check". Each one must make its property fail, which shows a pass means something. Trace validation accepted 2,000 governor runs and 1,100 outbox runs of the real code.

    Bugs found and fixed, by what found them

    Each one was replayed on the real code, fixed, and kept as a regression test. The model checker found the ordering bugs tests never reached: a notice told twice, a message overtaking a ticket's question, a reminder lost in a crash.

    Not proven yet

    • No run against a real language model yet. The checks prove the plumbing, not the judgement. vigil login codex then vigil eval is the first test.
    • The chat apps are tested only with fake channels. Pair one with /pair and use it for a few days.
    • The models cover small sizes and 8-hour time steps; they are strong evidence, not a proof for every size.
